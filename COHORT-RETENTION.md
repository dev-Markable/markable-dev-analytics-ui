# Cohort / Retention — спека вью

> Статус: **бэк готов ✅** (DevPulse-core + OAS `3.2.0`, тег `Cohorts` в `stats-contract`).
> Все три эндпоинта доступны: `/cohorts/retention`, `/cohorts/activity-matrix`,
> `/cohorts/tier-transitions`. Поддерживает направление C (лонгитюд) из
> [`README.md`](./README.md#roadmap).
>
> **Важно (отличие от первоначального proposal):** снапшоты **НЕ нужны** — всё, включая
> tier-transitions, считается из иммутабельной истории коммитов. `ActivityScorer` на бэке —
> чистая функция, поэтому уровень активности за любой прошлый месяц **пересчитывается** из
> агрегатов (не наблюдаемое состояние, как статус Kaiten-карточки в Flow). Phase 2 (снапшоты)
> из плана ниже **отпадает** — см. §5, §7.

## 1. Зачем и в чём отличие

Классический retention строят **от новых пользователей** (когорта = месяц
прихода). Нам это узко: мы хотим **историю про всех разработчиков сразу**, чтобы
наглядно, одним взглядом увидеть жизнь всей команды во времени:

- кто пришёл волнами (всплески найма / подключения репозиториев);
- кто **отвалился** (перестал коммитить) и когда;
- кто **стабильно активен** годами, а кто «вспыхнул и пропал»;
- возвращаются ли люди после паузы (re-activation).

То есть когорта — это **не только новички**: каждый разработчик попадает в одну
из когорт по своему первому активному месяцу, и вью покрывает **весь состав за
всю историю**, а не только последний приток.

**Активен в месяце** = есть ≥1 не-мердж коммита в этом месяце (порог настраивается).

## 2. Вью на странице `/cohorts`

Три взаимодополняющих среза. Уважают глобальный фильтр команды (`?team`); период
здесь — это **окно истории** (по умолчанию вся доступная история, не 30 дней).

### 2.1 Retention-треугольник (главный)

Когорта = месяц **первой** активности разработчика. Для когорты `C` и смещения
`k` месяцев: `retention[C][k] = доля разработчиков когорты C, активных в месяце C+k`.

- Строки — когорты (с размером `size`), колонки — смещение 0, 1, 2, … месяцев.
- `k=0` всегда 100%. Цвет ячейки — процент (heatmap, треугольная форма).
- Сразу видно: какие когорты «тают» быстро, какие держатся; есть ли общий
  паттерн оттока на N-м месяце.

### 2.2 Матрица активности (буквально «все»)

Heatmap **разработчик × месяц**: каждая строка — человек, колонка — месяц, цвет —
интенсивность (не-мердж коммиты, лог-шкала).

- Это и есть «история про всех»: видно линию жизни каждого — рамп, провалы, уход.
- Сортировка: по стажу (первый месяц), по суммарной активности, по команде.
- Группировка/фильтр по команде; поиск по разработчику.
- Клик по строке → профиль (переиспользуем drill-down паттерн).

### 2.3 Кривая удержания + переходы тиров (саммари)

- **Rolling retention curve** — усреднённая по всем когортам линия «доля активных
  через k месяцев». Один график «насколько липкая» инженерка в целом.
- **Матрица переходов тиров** (`INACTIVE → BELOW_AVERAGE → ACTIVE → STAR`):
  из тира T в месяце — куда ушли в следующем. Удержание не самого факта
  активности, а её **уровня**. Готово: `GET /cohorts/tier-transitions` (бэк пересчитывает
  тир за месяц из коммитов, снапшоты не нужны). 4×4 `matrix`, строки нормированы (сумма = 1).
  Трактовка: трактория считается от первого активного месяца разработчика до конца окна —
  ушедшие («churn») попадают в INACTIVE и там остаются, поэтому строка INACTIVE будет
  доминирована переходами `→ INACTIVE` (это и есть «кто отвалился и не вернулся»).

Переиспользуем: div-grid heatmap и цветовую шкалу (как `widgets/activity/heatmap`),
квантили/перцентили при необходимости, drill-down Drawer.

## 3. Источник данных

**Факт активности по месяцам на разработчика** — основа для 2.1 и 2.2 — выводится
из `/stats/daily` (`email` + `date` + `commits`/`mergeCommits`): группируем по
`(email, месяц)`. То есть **MVP реально собрать на клиенте**, запросив `daily` за
широкое окно (вся история). Ограничение — размер ответа: тысячи строк за годы.

**Уровень активности по месяцам** (`activity.category`/`score`) для 2.3 в `daily`
нет — но это **не упирается в снапшоты**: бэк пересчитывает score за каждый месяц из
коммит-агрегатов (`ActivityScorer` — чистая функция) и отдаёт готовую матрицу переходов
через `/cohorts/tier-transitions`. Клиенту считать score не нужно.

## 4. Контракт OAS — что хотим

Тег `Cohorts` (в `stats-contract`). Базовые параметры: `from?`/`to?` (окно истории; по
умолчанию вся), `team?` (по **текущей** команде). **Интервал зафиксирован = `month`** —
отдельного `interval?`-параметра в контракте нет (`week` — будущая аддитивная правка).
`minCommits?` (порог «активен», default 1) — **только у `/cohorts/retention`**;
`activity-matrix` и `tier-transitions` используют порог 1 неявно.

> Реальный контракт может слегка отличаться от схем-набросков ниже — сверяйтесь с
> сгенерёнными типами `@devpulse-dev/api-types@3.2.0` (`components['schemas']['CohortRetention'
> | 'CohortActivityMatrix' | 'TierTransitions']`).

### 4.1 `GET /cohorts/retention` — треугольник

```yaml
parameters: [from?, to?, team?, interval?, minCommits?]
responses:
  200:
    CohortRetention:
      interval: { type: string, enum: [month, week] }
      cohorts:
        - cohort: string        # 'YYYY-MM' (или 'YYYY-Www')
          size: int             # сколько разработчиков впервые активны в этот период
          retention: [number]   # доли 0..1 по смещению; retention[0] == 1
```

```ts
export type CohortRetention = Schemas['CohortRetention'];
```

### 4.2 `GET /cohorts/activity-matrix` — все разработчики × месяцы

```yaml
parameters: [from?, to?, team?, interval?]
responses:
  200:
    CohortActivityMatrix:
      months: [string]               # ось колонок, 'YYYY-MM' по возрастанию
      developers:
        - email: Email
          displayName: string | null
          avatarUrl: string | null
          team: string | null
          firstActive: string        # 'YYYY-MM'
          lastActive: string
          # cells выровнены по months: не-мердж коммиты за месяц (0 = неактивен)
          cells: [int]
```

```ts
export type CohortActivityMatrix = Schemas['CohortActivityMatrix'];
```

### 4.3 `GET /cohorts/tier-transitions` — переходы тиров (готово, без снапшотов)

```yaml
parameters: [from, to, team?]
responses:
  200:
    TierTransitions:
      # доля переходов из тира i в тир j период-к-периоду, усреднённая по окну
      tiers: [INACTIVE, BELOW_AVERAGE, ACTIVE, STAR]
      matrix: [[number]]             # 4×4, строки — откуда, сумма строки = 1
```

## 5. Что на бэке (`DevPulse-core`) — ✅ готово, без новых хранилищ

Все три эндпоинта считаются из существующих коммит-данных (`daily_author_stats`),
**снапшоты не нужны**:

1. `/cohorts/retention` и `/cohorts/activity-matrix` — **SQL GROUP BY (email, месяц)** за окно
   (`JdbcTemplate`, не тянем сырой daily в heap), `team` — подзапросом на `unified_user`.
   Доменный `CohortAssembler` строит треугольник/матрицу (чистая функция).
2. `/cohorts/tier-transitions` — тир за каждый месяц **пересчитывается** `ActivityScorer`'ом из
   коммит-агрегатов того месяца; копятся переходы месяц-к-месяцу. **Снапшоты НЕ нужны.**

**Почему ретроактивность работает (поправка к первоначальному proposal):** да, факт коммита
историчен. Но и **уровень активности (score) тоже** — это чистая функция от коммит-агрегатов,
которые историчны. Поэтому score за любой прошлый месяц восстанавливается пересчётом; «джоб,
накапливающий историю с момента запуска» **не требуется**. (Контраст с Flow-CFD, где статус
карточки Kaiten — наблюдаемое мутабельное состояние, прошлое которого без снапшотов не вернуть.)

**Оговорка про окно:** «первый активный месяц» когорты ограничен глубиной данных сбора (backfill
с начала истории коммитов). Кто коммитил до старта данных — его когорта искусственно = первый
месяц данных. Подписывайте ось как «когорты с начала сбора».

```
src/pages/cohorts/                  # CohortsPage: окно истории, табы вью
src/entities/cohort/
  ├── model/types.ts                # алиасы Schemas['Cohort*' / 'TierTransitions']
  └── api/{cohort.api.ts, queries.ts}

  ├── retention-triangle/           # треугольный heatmap (div-grid + цветошкала)
  ├── activity-matrix/              # разработчик × месяц, виртуализация строк
  └── retention-curve/              # rolling-кривая + матрица переходов
```

- **Данные — серверные `/cohorts/*`** (бэк готов): три `queryOptions`-фабрики, как у
  `stats`/`dashboard`. Клиентскую агрегацию из `/stats/daily` (`lib/build-cohorts.ts`) делать
  не нужно — серверные эндпоинты дешевле по трафику. `retention-curve` (rolling) фронт усредняет
  из `/cohorts/retention` сам.
- **Виртуализация** матрицы активности (`@tanstack/react-virtual`, уже в проекте)
  — сотни разработчиков × десятки месяцев.
- Навигация: `nav-items` + `ROUTES.cohorts` + пункт в `command-palette`.
- Lazy-роут; ключи запросов включают `team/window` (+ `minCommits` для retention) → авто-refetch.
  `interval` в ключ не кладём — он фиксирован `month`.

## 7. Фазирование

Бэк отдаёт **все три** эндпоинта серверно (агрегация в БД), поэтому Phase 0 (клиентская
агрегация из `/stats/daily`) и Phase 2 (снапшоты) из исходного плана **отпадают**:

- **MVP (всё сразу):** `/cohorts/retention` + `/cohorts/activity-matrix` +
  `/cohorts/tier-transitions` — три вью на странице. Клиентскую агрегацию из `/stats/daily`
  делать не нужно (серверные эндпоинты готовы, трафик меньше).
- **Аддитивно потом (не блокеры):** `interval=week` (бэк сейчас только `month`); rolling
  retention curve фронт строит из того же `/cohorts/retention` (усреднение по когортам, без бэка).
- **~~Phase 2 (снапшоты)~~** — не нужна.

## 8. Открытые вопросы

1. ✅ **Решено.** Порог «активен» — **не-мердж ≥ 1** (дефолт), настраивается через `minCommits?`
   на `/cohorts/retention`. Merge-коммиты не считаются (везде используется `nonMergeCommits`).
2. ✅ **Решено для MVP.** Интервал — **месяц** (зафиксирован, отдельного параметра нет).
   `week` — будущая аддитивная правка контракта.
3. Re-activation: вернувшийся после паузы засчитывается активным в своём
   смещении — это корректно для retention, но стоит подсветить в матрице (видно
   разрыв). *(Бэк: в `cells` будет 0 в месяцы паузы — фронт рисует разрыв.)*
4. ✅ **Подтверждено как есть.** Привязка к команде — **текущая** (`team?` фильтрует по
   `unified_user.team` сейчас), не историческая. Переход между командами в прошлом не отражён.
5. Часовой пояс границ месяца — как у `daily` (локальное время сервера сбора). Бэк группирует
   по `to_char(date,'YYYY-MM')` над уже-агрегированной датой коммита.
6. Анонимизация/доступ: матрица «все разработчики» — чувствительный обзор, при
   будущем auth ограничить ролью (лид видит свою команду). *(Бэк auth пока нет — открыто.)*
